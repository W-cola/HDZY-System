状态：面向后续开发的建议基线。代码现状和缺陷见 PROJECT_STATUS.md；未决业务口径见 DECISIONS.md。这里的“应当”不是对既有实现正确性的承诺。

## 1. 数据与迁移

- 业务数据必须落库；内存、示例数据只用于明确隔离的演示或测试。
- 运行时使用 utils/db.ts；允许停服阶段的独立迁移进程，但不能与 API 同时打开同一 PGlite 目录。不得在业务路由各自 new PGlite。
- 新结构变化追加递增 SQL 迁移，保留已执行迁移；兼容旧数据、记录版本、验证重复执行与中途失败恢复。不能以删除库、删除迁移记录或只改 001 解决升级。
- 种子补充缺失基础项；不得在每次启动覆盖用户修改的角色、权限、部门、岗位。历史修正需显式版本和影响说明。现有代码未满足此条，见 R04。
- 多表业务写入具有原子性。PostgreSQL 用同一 client 开始/提交/回滚事务并 finally release；PGlite 用其 transaction。移交、撤回、版本切换、批量导入要验证失败回滚。
- SQL 值使用参数化；动态排序/列名必须白名单。ID 应可抵抗并发碰撞，不新增仅依赖 Date.now 的主键方案。
- 备份同时覆盖数据库、附件及必要配置；实际恢复验证才算可恢复。PGlite 应先停写并完成关闭后进行一致性备份，不在运行时随意复制目录冒充可靠备份。

## 2. 权限

授权需要同时满足：账号有效 → 资源/操作权限 → 数据范围 → 当前业务状态允许。前端控制只改善体验，后端必须独立判断。

- 业务路由优先用 requirePermission 获取完整 AuthContext；不得把 verifyAccessToken 的 AuthUser 强转后传给 dataScopeCondition。
- 新增、编辑、删除、导入、上传、下载各自核验权限；UPSERT 不得让 create 覆盖 update 授权。
- 修改时先检查旧资源归属，再检查新引用对象是否可用；不能仅验证请求提供的新 customerId/contractId。
- 禁用账号、角色、菜单后应按约定及时失效；不能单靠 token 中旧角色长期放行。
- 菜单以授权后的后端结果为准；不要无条件前端补入缺失页面来掩盖权限问题。
- allRead 应限制写操作；allReadOwnWrite 应分别处理读取和写入数据范围。现有工具没有完整区分，修复前不得宣称已实现。
- super 与 admin 是否等价、多角色范围如何合并，尚待确认。新业务不能继续增加写死角色名的例外。
- 合同、员工、发票附件必须验证所属业务记录及相应权限；校验文件 ID 格式不等于授权。

新增权限应同一变更更新：菜单/权限定义 → 前端按钮/页面 → 后端检查 → 默认分配策略（如果明确需要）→ 多角色测试。默认分配只在受控初始化中应用，不在每次启动补回撤销权限。

## 3. 合同与财务口径

当前已实现：正式合同付款比例总和校验 100%（容差 0.001）；草稿允许较少资料但仍要求项目编号、合同名、客户。回款金额为正；销售提交状态被限制为待确认，财务可使用其他状态。

后续规则：

- 金额后端校验，并与数据库 numeric 精度一致；明确舍入位置，不依赖浏览器浮点合计作为最终依据。
- 合同金额、明细总额、付款计划金额是否必须相等由 D04 决定，不能由 AI 临时猜测。
- 开票额和回款额是两个维度；不得用“开票额 + 回款额 = 合同额”作为通用正确性约束。
- 统计必须明确计入哪些状态、如何处理作废/驳回/退款/超额。当前多种状态并存，新增统计前先核口径。
- 开票资料换版应保留历史；合同中保存的开票快照是否可随之变化要有明确规则。
- 删除或恢复涉及关联合同、发票、回款、商机时，保持关联一致；不假设所有模块都采用相同软删除机制。

## 4. API、页面与附件

- 复用 api/request.ts、api/core 与现有表格/表单封装，不在各页面复制另一套请求或权限体系。
- 服务端输入采用统一 schema、长度、枚举、数值边界与日期校验；更新和新增采用相容规则。
- 当前成功响应为 `{code:0,data,error:null,message:'ok'}`，业务失败可仍是 HTTP 200 且 code=-1；调用与测试必须检查业务 code。
- 附件目录使用 upload-paths.ts。上传限制大小和允许类型，文件名规范化；操作前核验关联资源，不在文档暴露原始敏感附件。
- 系统账号与员工档案是不同模型，未确认前不得自动互删、同步或强行建立一对一关系。

## 5. 工程与交付

- 默认不改框架核心。确需修改 packages 时先检查恢复机制和备份差异，验证正常运行与恢复后的行为一致。
- 一次任务明确目的、影响范围和验收；小需求不强制产生长篇计划文件。
- 源码、权限、数据迁移、测试及必要文档形成同一可追踪变更。记录未通过项，不以“应该没问题”关闭任务。
- 发布、真实数据迁移、破坏性清理在获得相应授权后执行；普通已授权开发任务无需重复询问许可。
